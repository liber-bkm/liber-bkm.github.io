---
title: JSON API internals
description: The api.go endpoint surface and the shared cores behind it.
---

`api.go` serves the JSON surface the native Android client talks to. All routes share the HTML handlers' cores (`store.Search`/`filterDeep`/`paginate`, `addBookmarkToStore`, `syncBookmarkFiles`, journal writes), so behavior can't drift between CLI, web UI, and API.

## Bookmarks

`GET /api/v1/bookmarks` lists with the same `q`/`scope`/`deep`/`sort`/`page` params and 500-page shape as `/`, plus add. `GET /api/v1/bookmarks/{id}` gets, edits, and deletes a single bookmark. JSON-native translations of form flows: duplicates answer 409 with the existing entry plus a confirm hint (`confirm_dup: true` adds anyway), deletes without `?confirm=true` describe instead of acting, PUT fields are pointers so absent means untouched (empty title/URL is 400), bodies are capped at 1MB. Attachments are read-only names in v1; managing them stays in the HTML UI. Auth rides on `withAuth` unchanged (bearer for scripts, cookie+CSRF for browsers, JSON 401 vs login redirect). See [Web auth](/dev/web-auth/).

## Tags and folders

`GET /api/v1/tags` lists tags with counts (`{"tags":[{"name","count"}]}`, count-descending then name, same order as `sortedTaxRows`), and `POST /api/v1/tags/rename` (`{"old","new"}`) plus `POST /api/v1/tags/delete` (`{"tag","confirm"}`) reuse the `taxonomy.go` cores under `writeMu` with journal writes, so CLI, HTML, and API tag behavior can't drift. Delete without `confirm: true` describes instead of acting (affected count plus hint, computed read-only so no files are touched); unknown tags are 404, empty/same-value renames are 400. `GET /api/v1/folders` (`{"folders":[{"name","display","count"}]}`, root carried as `name: ""` with `display: "/"`) plus `POST /api/v1/folders/rename` and `POST /api/v1/folders/delete` (delete moves the subtree back to the root, same as the CLI) reuse `renameFolder` the same way, with subtree counts for the describe path and 404 on empty matches. The native client's `TagsScreen`/`FoldersScreen` consume these calls (list, rename with dialog, delete with count dialog; the root folder's actions are disabled since the server rejects them); rule-learn is a later slice following the same pattern.

## Rules

`GET /api/v1/rules` lists rules with applied counts (`{"rules":[{"id","match","folder","tags","applied_count"}]}`, same count source as `--auto list`), `POST /api/v1/rules` (`{"match","folder","tags"}`) reuses `createRule` including backfill with a combined bookmark-plus-rule journal entry, `GET /api/v1/rules/suggestions` (`?min=N`, default 3, minimum 2) exposes `suggestRules`, `POST /api/v1/rules/learn` (`{"min"}`) creates every suggestion like `--auto learn --create` (already-covered hosts yield zero creations), `POST /api/v1/rules/apply` (`{"id"}` optional, absent means all) reuses `applyRules`, and `DELETE /api/v1/rules/{id}` describes (rule plus applied count) without `?confirm=true` and deletes with it, leaving classified bookmarks as-is. Rule editing with reapply stays CLI-only for now. The native `RulesScreen` (reached from the tags screen or settings) lists rules with per-row apply/delete, an add form, and a learn section with min field, suggestions preview, create-all, and apply-all. `PUT /api/v1/rules/{id}` (`{"match","folder","tags","reapply"}`, absent means keep, empty keeps per the core) reuses `editRule` with a combined journal entry and reports `reapplied`; unknown ids are 404. The native edit dialog prefills the form with a reapply checkbox.

## Profiles

`GET /api/v1/profiles` lists tracked profiles with paths and the active mark (`default` is the profile-less base dir), `POST /api/v1/profiles/switch` (`{"name"}`, `"default"` returns to the base) and `POST /api/v1/profiles/delete` (`{"name"}`) reuse `profileSwitchMsg`/`profileDeleteMsg` under `writeMu`. Delete only untracks, data stays on disk, the active profile can't be removed. The server is stateless per request, so a switch takes effect on the very next call; the native `ProfilesScreen` (reached from settings) pops back to the auto-loading list after a switch.

## Link health

`POST /api/v1/check/run` (`{"spec","workers","stale"}`) mirrors `/check/run`: same `resolveCheckTargets`/`scanCheckTargets`/`stampCheckTargets` cores (scan unlocked, then lock plus reload plus stamp plus save, stamps not journaled), same moved/dead/uncertain buckets with `{id,title,url,detail,target,status}` rows. `POST /api/v1/check/apply` (`{"id","action","target","confirm"}`) mirrors the per-row actions (`update`/`retitle`/`delete`/`quarantine`); `target` is required for update/retitle, delete without `confirm: true` describes, unknown actions and missing bookmarks are 400/404. The native `CheckScreen` (Check button on the list screen) runs a scan with spec/stale fields, drops rows locally as actions land (like `renderRemainingCheck`), and confirms deletes with a dialog. Scans stay synchronous like the web flow, so the client uses an extended read timeout for the run call; the background-run-plus-poll upgrade noted under Known future work would cover this endpoint first.

## Settings

`GET /api/v1/settings` exposes collection display data (`base_dir` effective, `active_profile`, effective `archive_backend`, bookmark/tag/folder/rule counts, `maintenance_status` from the same helper as the settings page) and `POST /api/v1/settings` (`{"archive_backend"}`) reuses the settings-save backend validation under `writeMu` with `SaveConfig`. Everything else on the settings page (tool commands, dir overrides, device id, sync, import/export, reindex, profiles) stays HTML/CLI-only: dir repointing and identity keys are too footgun-prone for a thin client, and file flows don't map onto the JSON API. The native `SettingsScreen` (Settings button on the list screen) shows the display data with a backend selector; the current backend renders marked and disabled.

## Saved content, notes, and attachments

`GET /api/v1/bookmarks/{id}/card|archive|markdown` serves the saved content as raw bytes (`text/html`): card and archive straight off disk via `ServeFile`, markdown through the extracted `markdownPageHTML` helper shared with the HTML handler. `GET .../attachments/{n}` (1-based, matching the v1 attachment order) serves the file with a `Content-Disposition` filename. The native `SavedScreen` fetches the HTML over the authenticated client and renders it in a framework `WebView` with JavaScript and network loads blocked (archives inline assets as data URIs, so nothing else is needed); attachments download to the app cache and open externally through a `FileProvider` (`file_paths.xml`, cache only). No new third-party deps: `AndroidView` and `FileProvider` ride the existing Compose/activity artifacts.

Markdown notes are editable on all three surfaces. `render.go` splits the file format into `markdownBody` (frontmatter strip, also reused by the renderer) and `buildMarkdownFile` (frontmatter regeneration plus a supplied body), so edits never desync frontmatter from the bookmark; `saveMarkdownBody` creates the copy when missing. The web edit page shows a notes textarea (copy-holders only), `PUT /api/v1/bookmarks/{id}` takes `markdown_text` (creates with the given body when there is no copy), and `GET .../markdown?raw=1` serves the raw source as `text/markdown`. Attachments graduate from read-only names: `POST .../attachments` (`{filename, content_base64}`, decoded through the same `attachReader` the CLI uses) and `DELETE .../attachments/{n}` both journal upserts. Base64-in-JSON was chosen over multipart for uploads: no new client deps, at the cost of the shared 1MB body cap bounding uploads to roughly 750KB. The native add screen takes a markdown toggle plus picked files (uploaded after create; a partial failure flips Add into Done so a retry can't duplicate), and the edit screen edits notes plus add/remove attachments inline. The add and edit screens also take a full-page archive toggle (the existing `archive` create/edit flags); archiving fetches the page synchronously server-side, so the client's add/update calls ride the extended-timeout OkHttp client instead of the default 30s one.

## History, bulk, and library

`GET /api/v1/history` returns open history most-recent-first from the shared `historyRows` core; the native `HistoryScreen` (History button on the list) opens details from its rows. `POST /api/v1/bulk` (`{"ids","action","tags","folder","confirm"}`) mirrors the web bulk bar: `tags` replaces, `folder` moves (absent means root), `delete` describes (count plus titles) without confirm, reusing the same cores, dedupe, and journal shapes. The native list enters selection mode on long-press, with a count top bar, checkboxes, and a Delete/Tags/Move bar with dialogs.

`POST /api/v1/library/import` (`{"content","markdown","archive"}`, capped by the shared 1MB body limit), `GET /api/v1/library/export` (Netscape download), `POST /api/v1/library/site` (optional `dir`, defaults to `<base>/site`), `POST /api/v1/sync` (`{"push"}`), and `POST /api/v1/reindex` (merge/all/prune/compact/prune_journal flags) reuse `importData`/`writeNetscapeExport`/`doExportSite`/`runSyncTo`/`runReindexWith`; sync and reindex answer 200 with `{output}` plus an `error` key on failure instead of 500, since partial output is the useful bit. The native `LibraryScreen` (reached from settings) picks an export file through the system picker, shares the Netscape export via `FileProvider`, and confirms prune/compact reindexes.
